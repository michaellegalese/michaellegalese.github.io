3:T51b3,<h1>Make rules read like law</h1>
<p>Write rules whose calls read like sentences, and whose rendered document reads like legal drafting.</p>
<p><strong>Before you start:</strong> <a href="/l4/tutorials/getting-started/first-l4-file">Install L4 and write your first rule</a>.</p>
<p>This page has two parts:</p>
<ol>
<li><strong>Infix, postfix and mixfix functions</strong>: put a rule's name and its inputs in natural word order, so <code>`the applicant` `is eligible for` `the programme`</code> is valid L4.</li>
<li><strong>Rendering</strong>: L4 can turn your rules back into an English document. Names, the shape of the code, and <code>@nlg</code> annotations decide how well it reads.</li>
</ol>
<hr>
<h2 id="infix-postfix-and-mixfix-functions">Infix, postfix and mixfix functions</h2>
<p>Most programming languages put the function name first: <code>isEligible(person, programme)</code>. In L4 the inputs can go before, between or after the words of the name:</p>
<table>
<thead>
<tr>
<th>Pattern</th>
<th>Definition</th>
<th>Call</th>
</tr>
</thead>
<tbody>
<tr>
<td>Prefix</td>
<td><code>`plus` a b MEANS ...</code></td>
<td><code>`plus` 3 5</code></td>
</tr>
<tr>
<td>Infix</td>
<td><code>a `plus` b MEANS ...</code></td>
<td><code>3 `plus` 5</code></td>
</tr>
<tr>
<td>Postfix</td>
<td><code>amount `percent` MEANS ...</code></td>
<td><code>50 `percent` </code></td>
</tr>
<tr>
<td>Mixfix</td>
<td><code>value `is between` lower `and` upper MEANS ...</code></td>
<td><code>5 `is between` 0 `and` 10</code></td>
</tr>
</tbody>
</table>
<p>The inputs are the names declared with <code>GIVEN</code>; every other word in the definition is part of the function's name. A call uses the same word order as the definition.</p>
<p><strong>Complete example:</strong></p>
<pre><code class="language-l4-file">§ `Natural Language Functions Tutorial`

-- This file demonstrates infix, postfix, and mixfix function patterns
-- that allow L4 code to read like natural language.

-- ============================================================================
-- INFIX FUNCTIONS
-- Pattern: param `keyword` param
-- ============================================================================

-- Simple numeric infix operator
GIVEN a IS A NUMBER, b IS A NUMBER
GIVETH A NUMBER
a `plus` b MEANS a + b

-- Multi-word infix operator
GIVEN person IS A STRING, program IS A STRING
GIVETH A BOOLEAN
person `is eligible for` program MEANS TRUE

-- Test infix calls
#EVAL 3 `plus` 5
#EVAL "Alice" `is eligible for` "Medicare"

-- Infix can also be called with prefix notation
#EVAL `plus` 10 20

-- ============================================================================
-- POSTFIX FUNCTIONS
-- Pattern: param `keyword`
-- ============================================================================

-- Simple postfix operator
GIVEN amount IS A NUMBER
GIVETH A NUMBER
amount `percent` MEANS amount / 100

-- Another postfix example
GIVEN n IS A NUMBER
GIVETH A NUMBER
n squared MEANS n * n

-- Test postfix calls
#EVAL 50 `percent`
#EVAL 75 percent
#EVAL 5 squared
#EVAL 7 `squared`

-- Postfix with expressions
#EVAL (10 + 5) `percent`

-- ============================================================================
-- TERNARY MIXFIX FUNCTIONS
-- Pattern: `keyword` param `keyword` param `keyword` param
-- ============================================================================

-- Custom conditional operator
GIVEN cond IS A BOOLEAN, thenVal IS A NUMBER, elseVal IS A NUMBER
GIVETH A NUMBER
`myif` cond `mythen` thenVal `myelse` elseVal MEANS
  IF cond THEN thenVal ELSE elseVal

-- Test ternary mixfix
#EVAL `myif` TRUE `mythen` 42 `myelse` 0
#EVAL `myif` FALSE `mythen` 42 `myelse` 0
#EVAL `myif` (1 = 1) `mythen` (10 + 5) `myelse` (20 - 5)

-- ============================================================================
-- QUATERNARY MIXFIX FUNCTIONS
-- Pattern: param `keyword` param `keyword` param `keyword` param
-- ============================================================================

GIVEN mummy IS A STRING, daddy IS A STRING, baby IS A STRING, nickname IS A STRING
GIVETH A STRING
mummy `and` daddy `had` baby `called` nickname MEANS baby

-- Test quaternary mixfix
#EVAL "Alice" `and` "Bob" `had` "Charlie" `called` "Chuck"

-- Prefix notation also works
#EVAL `and` "Mom" "Dad" "Kid" "Kiddo"

-- ============================================================================
-- ARITY-5 MIXFIX FUNCTIONS
-- ============================================================================

GIVEN a IS A NUMBER, b IS A NUMBER, c IS A NUMBER, d IS A NUMBER, e IS A NUMBER
GIVETH A NUMBER
a `op1` b `op2` c `op3` d `op4` e MEANS a + b + c + d + e

#EVAL 1 `op1` 2 `op2` 3 `op3` 4 `op4` 5
#EVAL (10 - 9) `op1` (1 + 1) `op2` 3 `op3` (2 * 2) `op4` 5

-- ============================================================================
-- RANGE CHECK MIXFIX
-- A practical example for legal conditions
-- ============================================================================

GIVEN lower IS A NUMBER, value IS A NUMBER, upper IS A NUMBER
GIVETH A BOOLEAN
lower `is at most` value `which is at most` upper MEANS
  lower &#x3C;= value AND value &#x3C;= upper

#EVAL 0 `is at most` 5 `which is at most` 10
#EVAL 0 `is at most` 15 `which is at most` 10

-- ============================================================================
-- PRACTICAL LEGAL EXAMPLE
-- Functions that read like legal prose
-- ============================================================================

DECLARE Person HAS
  name IS A STRING
  age IS A NUMBER

GIVEN person IS A Person
GIVETH A BOOLEAN
person `is an adult` MEANS person's age >= 18

GIVEN person IS A Person
GIVETH A BOOLEAN
person `is a minor` MEANS person's age &#x3C; 18

-- Create test data
`test adult` MEANS Person WITH name IS "Alice", age IS 30
`test minor` MEANS Person WITH name IS "Bob", age IS 15

-- Test legal predicates
#EVAL `test adult` `is an adult`
#EVAL `test minor` `is a minor`

-- ============================================================================
-- MIXFIX WITH WHERE CLAUSE
-- Defining helper operators locally
-- ============================================================================

GIVEN radius IS A NUMBER
GIVETH A NUMBER
`circle area for radius` radius MEANS
  radius `squared locally` TIMES pi
  WHERE
    pi MEANS 3.14159
    GIVEN r IS A NUMBER
    r `squared locally` MEANS r * r

#EVAL `circle area for radius` 10
</code></pre>
<h3 id="infix-one-input-on-each-side">Infix: one input on each side</h3>
<pre><code class="language-l4">GIVEN a IS A NUMBER
      b IS A NUMBER
GIVETH A NUMBER
a `plus` b MEANS a + b

#EVAL 3 `plus` 5
#EVAL `plus` 3 5
</code></pre>
<p>Both calls return <code>8</code>: a function defined in infix form can also be called in prefix form.</p>
<p>Names in backticks can contain spaces, so the name can be a whole phrase:</p>
<pre><code class="language-l4">DECLARE Person
    HAS `name`   IS A STRING
        `age`    IS A NUMBER
        `income` IS A NUMBER

GIVEN `the person` IS A Person
      `the threshold` IS A NUMBER
GIVETH A BOOLEAN
`the person` `has income above` `the threshold` MEANS
    `the person`'s `income` > `the threshold`

`Alice` MEANS Person WITH
    `name`   IS "Alice"
    `age`    IS 30
    `income` IS 50000

#EVAL `Alice` `has income above` 40000
</code></pre>
<h3 id="postfix-the-input-before-the-name">Postfix: the input before the name</h3>
<pre><code class="language-l4">GIVEN `the person` IS A Person
GIVETH A BOOLEAN
`the person` `is an adult` MEANS `the person`'s `age` >= 18

#EVAL `Alice` `is an adult`
</code></pre>
<p>For a one-word name, the backticks are optional at the call site: with <code>n `squared` MEANS n * n</code>, both <code>5 squared</code> and <code>5 `squared` </code> work.</p>
<h3 id="mixfix-words-and-inputs-interleaved">Mixfix: words and inputs interleaved</h3>
<p>A mixfix name has several words, with inputs between them:</p>
<pre><code class="language-l4">GIVEN value IS A NUMBER
      lower IS A NUMBER
      upper IS A NUMBER
GIVETH A BOOLEAN
value `is between` lower `and` upper MEANS
    lower &#x3C;= value AND value &#x3C;= upper

#EVAL 5 `is between` 0 `and` 10

GIVEN principal IS A NUMBER
      rate      IS A NUMBER
      term      IS A NUMBER
GIVETH A NUMBER
`simple interest on` principal `at` rate `percent for` term `years` MEANS
    principal * rate / 100 * term

#EVAL `simple interest on` 1000 `at` 5 `percent for` 3 `years`
</code></pre>
<p>The calls return <code>TRUE</code> and <code>150</code>. There is no limit on the number of inputs.</p>
<h3 id="points-to-watch">Points to watch</h3>
<ul>
<li><strong>List the inputs in <code>GIVEN</code> in the order they appear in the definition.</strong> For <code>value `is between` lower `and` upper</code>, the <code>GIVEN</code> must list <code>value</code>, <code>lower</code>, <code>upper</code>, in that order.</li>
<li><strong>An input cannot share a name with a word of the function name.</strong> <code>`percent for` years `years`</code> is an error; call the input <code>term</code>.</li>
<li><strong>Use parentheses</strong> when an argument is itself an expression: <code>(1 + 2) `plus` (3 + 4)</code>.</li>
<li><strong>Define local helpers in <code>WHERE</code>.</strong> A <code>WHERE</code> block can hold a full <code>GIVEN ... MEANS</code> definition, mixfix ones included; the complete example shows one.</li>
</ul>
<p>For the exact rules of how L4 matches mixfix calls, see <a href="/l4/reference/functions#mixfix-functions">Mixfix functions</a>.</p>
<hr>
<h2 id="render-your-rules-as-a-document">Render your rules as a document</h2>
<p>L4 can render your rules as formatted English, in the VS Code <strong>Render</strong> tab or with <code>l4 render file.l4 --format text</code>. The renderer is deterministic: it walks your code and turns each construct into a sentence or an outline. So the quality of the prose is mostly in your hands. Well-named, well-shaped rules read almost like professional drafting with no extra effort; badly named ones read like a transcript of an algorithm.</p>
<p>Three levers, from the cheapest to the most precise:</p>
<ol>
<li><strong>Names</strong>: backticked identifiers and input names.</li>
<li><strong>Shape</strong>: mixfix word order, control flow, arithmetic and section headings.</li>
<li><strong><code>@nlg</code></strong>: a sentence you write that replaces the generated one.</li>
</ol>
<hr>
<h2 id="names-do-most-of-the-work">Names do most of the work</h2>
<p>The renderer prints names as you wrote them. Good names are the most effective thing you can do.</p>
<p><strong>Name rules as the phrase you want to read.</strong> A backticked name can contain spaces:</p>
<pre><code class="language-l4">`monthly property tax` MEANS 250
mpt MEANS 250
</code></pre>
<p>The first renders as "Monthly property tax means 250."; the second as "Mpt means 250."</p>
<p><strong>Name inputs as nouns, not letters.</strong> Inputs appear in the prose and in every <code>@nlg</code> slot:</p>
<pre><code class="language-l4">GIVEN `the purchase price` IS A NUMBER
      `the deposit paid`   IS A NUMBER
GIVETH A NUMBER
`the balance due` MEANS `the purchase price` MINUS `the deposit paid`

GIVEN p IS A NUMBER
      d IS A NUMBER
GIVETH A NUMBER
`balance` MEANS p MINUS d
</code></pre>
<p>The first renders as "The balance due equals the purchase price − the deposit paid."; the second as "Balance equals p − d."</p>
<p>Legal writing sometimes uses letters on purpose, as in "A person (A) discriminates against another (B) if …" (Equality Act 2010, s.13). There, single letters are the right choice.</p>
<p>When an input has a record type, the renderer refers to it by the type's name: with <code>GIVEN claim IS A `Payment Claim`</code>, <code>claim's `amount`</code> renders as "the payment claim's amount". This works well when only one input has that type; two inputs of the same type would share the same phrase.</p>
<p><strong>Name record fields readably.</strong> A field renders as "X's field", so field names go straight into the prose:</p>
<pre><code class="language-l4">DECLARE `Property Details`
    HAS `market value`         IS A NUMBER
        `monthly property tax` IS A NUMBER
</code></pre>
<hr>
<h2 id="shape-the-code-so-it-reads-in-order">Shape the code so it reads in order</h2>
<p><strong>Use mixfix so calls read as sentences.</strong> Put the words and the inputs where they belong in the sentence:</p>
<pre><code class="language-l4">DECLARE Person    HAS `age`           IS A NUMBER
DECLARE Programme HAS `minimum age`   IS A NUMBER

GIVEN `the applicant` IS A Person
      `the programme` IS A Programme
GIVETH A BOOLEAN
DECIDE `the applicant` `is eligible for` `the programme` IF
    `the applicant`'s `age` AT LEAST `the programme`'s `minimum age`
</code></pre>
<p><strong>End helper names with a preposition.</strong> When a function's name ends in a word such as <code>of</code>, <code>for</code>, <code>to</code> or <code>between</code>, its arguments are joined naturally:</p>
<pre><code class="language-l4">GIVEN x IS A NUMBER
      y IS A NUMBER
GIVETH A NUMBER
`the later of` x y MEANS IF x >= y THEN x ELSE y

`start date` MEANS 3
`end date`   MEANS 7
`the deadline` MEANS `the later of` `start date` `end date`
</code></pre>
<p>The call renders as "the later of start date and end date". The same function named <code>`maximum`</code> renders as "maximum with start date and end date".</p>
<p><strong>Let control flow stay structured.</strong> <code>CONSIDER</code>, <code>IF</code>/<code>THEN</code>/<code>ELSE</code> and <code>AND</code>/<code>OR</code> render as indented outlines, not run-on sentences, so keep the operative logic where the renderer can see it:</p>
<pre><code class="language-l4">DECLARE Status IS ONE OF Paid, Overdue
DECLARE Claim HAS `status` IS A Status

GIVEN claim IS A Claim
GIVETH A STRING
`the reminder` MEANS
    CONSIDER claim's `status`
    WHEN Paid    THEN "none"
    WHEN Overdue THEN "send a reminder"
</code></pre>
<p>renders as</p>
<pre><code>• The reminder is determined by:
    depending on the claim's status:
    - if it is Paid: none
    - if it is Overdue: send a reminder
</code></pre>
<p><strong>Keep arithmetic as arithmetic.</strong> Numeric expressions render as formulas, with <code>+ − × ÷</code> and parentheses, not as "the sum of the product of …":</p>
<pre><code class="language-l4">`base rent`      MEANS 1000
`service charge` MEANS 100
`months`         MEANS 12
`deposit`        MEANS 2000

`the total payable` MEANS (`base rent` PLUS `service charge`) TIMES `months` PLUS `deposit`
</code></pre>
<p>renders as "The total payable equals (base rent + service charge) × months + deposit."</p>
<p><strong>Group rules into titled sections.</strong> <code>§ `Name`</code> starts a section and <code>§§ `Name`</code> a subsection (<code>§§§</code> goes deeper). Every declaration after a marker belongs to that section until the next marker. Sections become headings in the rendered document and entries in its table of contents:</p>
<pre><code class="language-l4">DECLARE Person HAS `age` IS A NUMBER

§ `Eligibility`

GIVEN `the applicant` IS A Person
GIVETH A BOOLEAN
DECIDE `the applicant` `qualifies` IF
    `the applicant` `is of working age`

§§ `Age requirements`

GIVEN `the applicant` IS A Person
GIVETH A BOOLEAN
DECIDE `the applicant` `is of working age` IF
    `the applicant`'s `age` AT LEAST 18
</code></pre>
<p>With <strong>Number sections</strong> turned on in the Render tab (or <code>--number-sections</code> on the command line), the headings are numbered: <code>§ 2  Eligibility</code>, then <code>2.1  Age requirements</code>. A file with no section markers is still grouped into automatic <strong>Definitions</strong> and <strong>Provisions</strong> sections, but your own markers let you name and order the parts the way a reader of the contract or statute expects.</p>
<hr>
<h2 id="nlg-annotations"><code>@nlg</code> annotations</h2>
<p>When names and shape are not enough (a recursive helper, a term of art, a formula you would rather state in words), add an <code>@nlg</code> annotation. It is the natural-language form of the definition and replaces the generated sentence.</p>
<p>Write <code>@nlg</code> at the end of the definition's line, after the name and inputs, with the body on the next line. Inside the sentence, <code>%name%</code> is a slot for an input; an input whose name has spaces keeps its backticks: <code>%`the principal`%</code>.</p>
<pre><code class="language-l4">GIVEN x IS A NUMBER
      y IS A NUMBER
GIVETH A NUMBER
`bigger` x y @nlg whichever is larger of %x% and %y%
  MEANS IF x >= y THEN x ELSE y

`start date` MEANS 3
`end date`   MEANS 7
`the deadline` MEANS `bigger` `start date` `end date`
</code></pre>
<p>Each slot is filled with the input's name in the definition itself, and with the actual argument at each call:</p>
<pre><code>• Bigger means whichever is larger of x and y.
• The deadline means whichever is larger of start date and end date.
</code></pre>
<p><strong>It replaces the body.</strong> A function with <code>@nlg</code> renders as its sentence, not as its implementation. That is what makes recursive library functions readable; the prelude's <code>filter</code> has <code>@nlg the items of %list% for which %f% holds</code>, so a call reads as a sentence instead of exposing the recursion.</p>
<table>
<thead>
<tr>
<th>Situation</th>
<th>Why <code>@nlg</code> helps</th>
</tr>
</thead>
<tbody>
<tr>
<td>Recursive or higher-order helpers</td>
<td>Describes the result, hides the implementation</td>
</tr>
<tr>
<td>A formula better said in words</td>
<td>"the pro-rated premium" instead of the arithmetic</td>
</tr>
<tr>
<td>Terms of art</td>
<td>Matches the exact statutory or contractual wording</td>
</tr>
<tr>
<td>A name that cannot be both valid code and good prose</td>
<td>Separates the two</td>
</tr>
</tbody>
</table>
<p>Tips:</p>
<ul>
<li>Use only the function's own inputs as slots, and write the sentence so that it reads well with each slot as a noun phrase.</li>
<li>Try names and shape first. An <code>@nlg</code> sentence can drift away from the logic it describes, so use it where it pays off.</li>
<li>One sentence per definition. For branching prose, let <code>CONSIDER</code> or <code>IF</code> render as an outline instead.</li>
</ul>

<h2 id="putting-it-together">Putting it together</h2>
<p>Before, with short names and no annotation:</p>
<pre><code class="language-l4">GIVEN p IS A NUMBER
      r IS A NUMBER
      n IS A NUMBER
GIVETH A NUMBER
pmt p r n MEANS p TIMES r DIVIDED BY (1 MINUS EXPONENT (1 PLUS r) (0 MINUS n))
</code></pre>
<p>This renders as "Pmt equals p × r ÷ (1 − EXPONENT with the sum of 1 and r and the difference between n and 0)."</p>
<p>After, with descriptive names and one <code>@nlg</code>:</p>
<pre><code class="language-l4">GIVEN `the principal`      IS A NUMBER
      `the monthly rate`   IS A NUMBER
      `the term in months` IS A NUMBER
GIVETH A NUMBER
`the monthly repayment` `the principal` `the monthly rate` `the term in months` @nlg the level monthly repayment on %`the principal`% at %`the monthly rate`% over %`the term in months`%
  MEANS     `the principal` TIMES `the monthly rate`
        DIVIDED BY (1 MINUS EXPONENT (1 PLUS `the monthly rate`) (0 MINUS `the term in months`))

`the loan`          MEANS 10000
`the interest rate` MEANS 0.01
`the term`          MEANS 12
`the repayment`     MEANS `the monthly repayment` `the loan` `the interest rate` `the term`
</code></pre>
<p>Now the call renders as "The repayment means the level monthly repayment on the loan at the interest rate over the term.", a sentence a lawyer can check.</p>

<h2 id="refine-the-style-with-legalese-ai">Refine the style with Legalese AI</h2>
<p>The renderer gives a faithful, deterministic baseline: the same input always gives the same prose, and it never adds facts. House style, tone and jurisdiction conventions are editorial choices that deterministic rules should not make.</p>
<p>Once the rendered output is accurate, Legalese AI can apply <strong>drafting policies</strong> to it: reusable style rules such as "use plain English", "prefer the active voice", "expand defined terms on first use", or a firm's house style. It rewrites the rendered prose to match, while staying anchored to the deterministic output so the meaning is kept.</p>
<p>Names, shape and <code>@nlg</code> get the content right; drafting policies get the style right. See <a href="/l4/tutorials/llm-integration/composing-l4-with-ai">Draft rules with Legalese AI</a> for how Legalese AI fits into writing rules.</p>

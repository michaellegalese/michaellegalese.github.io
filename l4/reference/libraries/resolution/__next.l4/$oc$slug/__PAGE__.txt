3:T4412,<h1>How IMPORT finds libraries</h1>
<p>This page is for people who run L4 tooling or develop the standard library. For how to write an <code>IMPORT</code>, see <a href="/l4/reference/libraries#import">IMPORT</a>.</p>
<p>When an L4 file says <code>IMPORT prelude</code>, the toolchain has to find <em>a</em> file
called <code>prelude</code> — but on a developer's machine there may be <strong>several</strong>: one
compiled into the binary, one in each git worktree, one in a machine-global
store, one shipped inside the VSCode extension. This page explains, in order:</p>
<ol>
<li><a href="#the-resolution-order">the resolution order and why each tier exists</a></li>
<li><a href="#the-devprod-playbook">the dev/prod playbook — what to set in each situation</a></li>
<li><a href="#reading-the-resolvers-output">how to read the resolver's logs and warnings</a></li>
<li><a href="#the-embed-staleness-gotcha">the embed-staleness gotcha</a> (why <code>cabal build</code>
doesn't pick up your prelude edit)</li>
</ol>
<p>An as-built description of the code behind all of this lives in
<code>specs/as-built/import-resolution.md</code> in the repository.</p>
<hr>
<h2 id="the-resolution-order">The resolution order</h2>
<p>For a bare module name <code>&#x3C;mod></code>, resolution tries, <strong>first match wins</strong>:</p>

<p>The XDG store is the <code>jl4/libraries</code> folder of the user's data directory.
It is <code>$XDG_DATA_HOME/jl4/libraries/</code> when that variable is set to an absolute path.
Otherwise it is <code>~/.local/share/jl4/libraries/</code> on macOS and Linux, and <code>%APPDATA%\jl4\libraries\</code> on Windows, which is usually <code>C:\Users\&#x3C;you>\AppData\Roaming\jl4\libraries\</code>.
Every other mention of <code>~/.local/share/jl4/libraries/</code> on this page means this folder.</p>
<p>Three rules of thumb fall out of the table:</p>
<ul>
<li><strong>Project-scoped beats embedded.</strong> If you put a <code>prelude.l4</code> in your project
root or beside the importing file, you get it. Overriding the stdlib is a
conscious, visible act — the file is <em>in your project</em>.</li>
<li><strong>Embedded beats ambient.</strong> A machine-global file (XDG, bundle) can never
silently replace the stdlib your binary was built with. Ambient tiers only
serve modules the embed does not carry.</li>
<li><strong><code>JL4_LIBRARY_PATH</code> is absolute.</strong> When it is set, the embedded copy is not
consulted <em>at all</em> — the operator has taken full control of the library
store. (The ambient tiers are still searched after it, for extras.)</li>
</ul>
<p><strong><code>jl4-service</code> uses a shorter ladder.</strong> A service that runs bundles other
people uploaded cannot let its own machine stand in for the standard library.
So a deployment's <code>IMPORT</code>s are resolved against the bundle's own files (tier 0)
and then the standard library built into the service binary (tier 4), and
nothing else. <strong>The service reads neither <code>JL4_LIBRARY_PATH</code>, nor its working
directory, nor the XDG store (<code>~/.local/share/jl4/libraries/</code>)</strong>, and not the
extension bundle either: tiers 1, 2, 3, 5 and 6 are not consulted. A
<code>prelude.l4</code> in the service's working directory, or a library directory exported
into its environment, has no effect on any deployment. (Without this rule it
would: the deploy reports "applied" and every call then answers 422 <code>sum is not in scope</code>.) The service says at start-up, at <code>WARN</code>, when <code>JL4_LIBRARY_PATH</code> is
set and therefore ignored.</p>
<p>A consequence for anyone moving a deployment onto the service: a library you
used to supply from the host's filesystem has to be a file in the bundle, in the
same directory as the file that imports it. A file elsewhere in the bundle is
found only when its directory happens to be the one the service treats as the
bundle's root, the directory of the first file in the bundle's sort order, so
do not rely on it.</p>
<p>A bundle that ships a file with the name of a standard library module, such as
its own <code>prelude.l4</code>, is still honoured, as any project copy is: the importers
that can see that file — those in the same directory — get it instead of the
library's. The service says so, at <code>WARN</code>, each time it compiles such a bundle
(<code>Bundle file stands in for a standard library module</code>, naming the file and the
module), unless the file is exactly the library's own text.</p>
<p>An <code>IMPORT</code> that finds nothing — no file in the bundle, no module in the built-in
library — does not stop the deploy, which still reports "applied": the file
typechecks, and only a call that reaches something the missing module should have
defined fails. The service logs a <code>WARN</code> for each one, naming the deployment, the
importing file and the module (<code>Bundle IMPORT resolves to nothing</code>), when the
bundle is compiled, which a restart does again from the stored sources. A refusal at
deploy time is not made; it would need a ruling of its own.</p>
<p>This ordering is pinned by tests: <code>jl4-lsp/test/LibraryResolutionSpec.hs</code>
(unit, table-driven), the <code>l4 library resolution shadow (B′)</code> group in
<code>jl4/tests-cli/Main.hs</code> (black-box CLI), and, for the service's shorter ladder,
<code>jl4-service/test/StdlibResolutionSpec.hs</code> and
<code>jl4-service/test/UnresolvedImportSpec.hs</code>.</p>

<h2 id="the-devprod-playbook">The dev/prod playbook</h2>
<h3 id="im-writing-l4-programs-consuming-the-stdlib">I'm writing L4 programs (consuming the stdlib)</h3>
<p>Do nothing. The embedded copy serves <code>IMPORT prelude</code> and friends, and it is
guaranteed to match the binary you're running. This is the <strong>prod</strong> regime:
an installed <code>l4</code>, the VSCode extension, <code>jl4-service</code> — none of them need any
environment setup or files on disk.</p>
<p><strong>Reading the stdlib from your editor.</strong> Go-to-definition on a stdlib name (say
<code>sum</code>, after <code>IMPORT prelude</code>) opens a <strong>read-only</strong> tab named <code>prelude.l4</code>.
It is not a file on disk: its address is <code>jl4-embedded:/prelude.l4</code>, and the
language server supplies the text — the exact copy compiled into the binary, so
what you read is what your program runs. Hover and go-to-definition work inside
it. To change the stdlib, edit <code>jl4-core/libraries/</code> and see the next section.</p>
<p>The limits: this works in the VSCode extension, which asks the server for the
text with a custom request, <code>l4/embeddedLibrary</code> (params <code>{"uri": …}</code>, reply
<code>{"text": …}</code>). Another editor connected to <code>jl4-lsp</code> receives the same
<code>jl4-embedded:</code> address and has to make the same request to show it. When
<code>JL4_LIBRARY_PATH</code> is set, the embedded copy is not consulted and
go-to-definition lands on a real file instead.</p>
<h3 id="im-developing-the-standard-library-itself-editing-jl4-corelibrariesl4">I'm developing the standard library itself (editing <code>jl4-core/libraries/*.l4</code>)</h3>
<p>Pin the resolver at your worktree, in the shell where you build and test:</p>
<pre><code class="language-sh">export JL4_LIBRARY_PATH="$PWD/jl4-core/libraries"
</code></pre>
<p>This is <strong>the</strong> reliable way to see your stdlib edits take effect, because of
the <a href="#the-embed-staleness-gotcha">embed-staleness gotcha</a> below: a plain
<code>cabal build</code> does <em>not</em> refresh the embedded copy, so without the pin your
freshly-edited prelude loses to the stale embed on every bare <code>IMPORT</code>.</p>
<p>Do <strong>not</strong> try to accomplish this with symlinks in
<code>~/.local/share/jl4/libraries/</code> pointing into a checkout. That was the old
convenience and it is what this ordering guards against: with several
worktrees, a machine-global symlink points at <em>one</em> of them and silently lies
to all the others. It also no longer works for stdlib modules, because the
embedded copy outranks the XDG store; the env var is both safer and the only
supported mechanism.</p>
<h3 id="im-running-the-test-suites">I'm running the test suites</h3>
<ul>
<li><strong>CI</strong> exports <code>JL4_LIBRARY_PATH</code> already.</li>
<li><strong><code>jl4-test</code> (the golden suite)</strong> sets it for you if unset (pointing at the
jl4-core datadir), so a bare <code>cabal test jl4-test</code> works. Locally you still
want the worktree pin from the previous section so the goldens run against
the sources you're editing.</li>
<li><strong><code>l4-cli-test</code></strong>: the library-resolution cases manufacture their own
environment per case (a fabricated <code>XDG_DATA_HOME</code>, the variable dropped), so
they need nothing set. The rest of the suite runs in the environment it is
given.</li>
</ul>
<h3 id="im-packaging-deploying">I'm packaging / deploying</h3>
<p>The embedded copy is the source of truth for a deployed binary. The VSCode
extension additionally ships <code>libraries/*.l4</code> next to the bundled binary
(tier 6); since the embed already carries the full stdlib, that directory only
matters for libraries <em>not</em> in the embed. (Whether it can be dropped entirely
is an open question — see §6 in <code>specs/as-built/import-resolution.md</code>.)
<code>jl4-service</code> consults neither: see
<a href="#the-resolution-order">the shorter ladder above</a>.</p>
<h3 id="i-want-machine-global-extra-libraries">I want machine-global extra libraries</h3>
<p><code>~/.local/share/jl4/libraries/</code> is still searched — <em>below</em> the embed. Use it
for third-party or personal libraries that are not part of the stdlib. Do not
use it to shadow stdlib modules; it can't anymore, and if a differing copy of
any module sits there you'll get a warning (next section).</p>
<hr>
<h2 id="reading-the-resolvers-output">Reading the resolver's output</h2>
<p>All of the following appears only when <code>JL4_LIBRARY_PATH</code> is <strong>unset</strong> (in the
env-pinned regime you have explicitly chosen your store, and the logs keep the
historical one-line form).</p>
<p><strong>The winner</strong>, at Info priority, with its position in the candidate order and
— when the path is a symlink — its real target:</p>
<pre><code>Info | [Import Resolution] Found in embedded libraries (candidate 3 of 5): prelude
Info | [Import Resolution] Found on filesystem (candidate 1 of 5): /work/prelude.l4
</code></pre>
<p>(The first when nothing in the project shadows the stdlib, the second when the
project root holds its own <code>prelude.l4</code>.)</p>
<p><strong>The full candidate table</strong>, at Debug priority:</p>
<pre><code>Debug | [Import Resolution] Candidate order for prelude: [1] project root: /work/prelude.l4 (miss); [2] importer-relative: /work/sub/prelude.l4 (miss); [3] embedded stdlib (compiled into this binary) (hit); [4] XDG data dir: /home/dev/.local/share/jl4/libraries/prelude.l4 (miss); [5] VSCode bundle: … (miss)
</code></pre>
<p><strong>The shadow warning</strong>, at Warning priority — the one you must never ignore.
It fires (once per session per configuration) when more than one copy of a
module is visible <strong>and their contents differ</strong>; byte-identical copies stay
silent. Symlinks are dereferenced so you can see <em>which checkout</em> an entry
really points at:</p>
<pre><code>Warning | [Import Resolution] Multiple differing copies of module `prelude` are visible:
  [chosen]   embedded stdlib (compiled into this binary)
  [shadowed] XDG data dir: /home/dev/.local/share/jl4/libraries/prelude.l4 -> /home/dev/src/other-checkout/jl4-core/libraries/prelude.l4
The [chosen] copy is used wherever this module is imported. To use a
different copy, set JL4_LIBRARY_PATH or place prelude.l4 in the project root or beside the importing file.
</code></pre>
<p>The CLI (<code>l4 check</code>, <code>l4 run</code>, …) prints Warning-level resolution lines to
stderr; Info/Debug lines are visible in the LSP log channel only.
<code>l4 check --json</code> and <code>l4 run --json</code> carry the same Warning lines in the
<code>diagnostics</code> array of their output, so a program that reads that array sees a
shadow warning there too.</p>
<p>An <code>IMPORT</code> that resolves to nothing is announced once, at Warning priority, as
<code>Module not found: myhelpers</code>: once for each importing file, however many of the
toolchain's rules go looking for the import. (<code>l4 ast</code>, which never
typechecks, prints that one line on stderr and exits 0.) The diagnostic that
accompanies it is described under <a href="/l4/reference/errors#module-not-found">Module not found</a>.</p>
<p>When two tiers name the same file — the CLI sets the project root to the
importing file's own directory, so the root tier and the importer-relative tier
probe one path — the shadow warning lists that file once, not as both
<code>[chosen]</code> and <code>[shadowed]</code>.</p>
<p><strong>Debugging "my edit didn't take effect":</strong></p>
<ol>
<li>Run <code>l4 check</code> on the importing file and read stderr. A shadow warning
tells you immediately that two differing copies exist and which one won.</li>
<li>No warning? Then only one copy is visible — check the winner line in the
language server's log to see
<em>which</em> one, and remember the embed-staleness gotcha: the embedded copy may
be older than your checkout.</li>
<li>When in doubt, <code>export JL4_LIBRARY_PATH="$PWD/jl4-core/libraries"</code> and
re-run. If behaviour changes, you were not loading the file you thought.</li>
</ol>

<h2 id="the-embed-staleness-gotcha">The embed-staleness gotcha</h2>
<p>The embedded stdlib is captured at <strong>build</strong> time by a Template Haskell splice
(<code>L4.API.EmbeddedLibraries</code>), which reads <code>libraries/*.l4</code> while GHC compiles
that module. For a checkout it reads the checkout's own <code>jl4-core/libraries/</code>
(the dependency GHC records is <code>&#x3C;checkout>/jl4-core/libraries/prelude.l4</code>, with
a content hash), so GHC itself would re-embed a library that changed. The catch
is that Cabal does not ask it to.</p>
<p>Measured on 2026-10-13, a checkout built with <code>cabal build</code> (GHC 9.10.3,
Cabal 3.16):</p>
<ul>
<li>Appending a definition to <code>jl4-core/libraries/prelude.l4</code> and running
<code>cabal build</code> prints <code>Up to date</code>. Nothing is rebuilt, and the binary keeps
serving the old prelude. <code>touch</code>-ing <code>L4.API.EmbeddedLibraries</code> changes
nothing either: Cabal compares content, not modification times.</li>
<li>The same edit plus any real change to a <code>jl4-core</code> source file (the test was a
comment on an unrelated module) makes Cabal call GHC. GHC sees the new content
hash, recompiles <code>L4.API.EmbeddedLibraries</code>, and the rebuilt binary serves the
new prelude.</li>
</ul>
<p>Consequences:</p>
<ul>
<li>Editing <code>jl4-core/libraries/prelude.l4</code> in a worktree and running a plain
<code>cabal build</code> leaves the binary on the old prelude.</li>
<li>To force a re-embed without the pin: make a real content change to a
<code>jl4-core</code> source file, or clean-rebuild <code>jl4-core</code>.</li>
<li>Which is why the supported dev workflow is the <code>JL4_LIBRARY_PATH</code> pin, not
"rebuild and hope". The pin outranks the embed deterministically.</li>
</ul>
<p>This was measured for a checkout. A build from somewhere else — <code>cabal install</code>
from an sdist, a Nix build — reads the <code>libraries/</code> of the directory it is built
in; this page does not claim to have measured those.</p>
<p>This is documented at the code site too
(<code>jl4-core/src/L4/API/EmbeddedLibraries/TH.hs</code>) and in
<code>jl4-core/libraries/README.md</code>.</p>

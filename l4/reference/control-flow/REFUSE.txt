1f:T4020,<h1>REFUSE</h1>
<p><code>REFUSE "reason"</code> declines to answer, and gives the reason.
Rules encode some cases and leave others out: a fee schedule may start in the year 2000, or a scheme may leave the case of a minor to an officer.
Where a rule reaches a case it does not encode, <code>REFUSE</code> gives no answer rather than a wrong one, and says why, and the tools that evaluate L4 report it as a refusal, with that reason (<a href="#what-each-tool-shows">What each tool shows</a>).</p>
<h2 id="syntax">Syntax</h2>
<pre><code class="language-text">REFUSE "reason"
</code></pre>
<p>The reason is a string literal, written as a reader should see it.
A <code>REFUSE</code> stands wherever a value can, whatever the type of that value: a rule that gives a number, a <code>BOOLEAN</code> or a record can refuse.</p>
<p><strong>Example file:</strong></p>
<pre><code class="language-l4-file">-- REFUSE examples

-- One definition for each reason a rule declines to answer,
-- named for what is not encoded.

GIVETH A NUMBER
`fees before 2000 are not encoded` MEANS
    REFUSE "this schedule is not encoded for years before 2000"

GIVEN year IS A NUMBER
GIVETH A NUMBER
`the fee in` year MEANS
    IF year >= 2000
    THEN 100
    ELSE `fees before 2000 are not encoded`

#EVAL `the fee in` 2024
#EVAL `the fee in` 1999

-- A rule that answers yes or no refuses the same way.
-- It has no query plan, because it may refuse.

GIVETH A BOOLEAN
`the insurance of a minor is not modelled` MEANS
    REFUSE "the insurance of a minor is not modelled"

GIVEN adult   IS A BOOLEAN
      insured IS A BOOLEAN
GIVETH A BOOLEAN
DECIDE covered IS
    IF adult
    THEN insured
    ELSE `the insurance of a minor is not modelled`

#EVAL covered TRUE TRUE
#EVAL covered FALSE TRUE

-- A REFUSE written inside a condition. `l4 render` lists it among the
-- conditions that must all be true.

GIVEN adult IS A BOOLEAN
GIVETH A BOOLEAN
DECIDE `may travel` IF
    adult AND REFUSE "travel is not modelled"

#EVAL `may travel` FALSE
#EVAL `may travel` TRUE

-- One refusal, for rules of any type.

GIVEN a IS A TYPE
GIVETH AN a
`not written yet` MEANS
    REFUSE "this rule has not been written yet"

GIVETH A NUMBER
`the deposit` MEANS 1 PLUS `not written yet`

GIVETH A BOOLEAN
`the deposit is refundable` MEANS `not written yet`

#EVAL `the deposit`
#EVAL `the deposit is refundable`

-- AND, OR and IF read from left to right, and stop as soon as the
-- answer is known.

#EVAL FALSE AND `the insurance of a minor is not modelled`
#EVAL `the insurance of a minor is not modelled` AND FALSE
#EVAL TRUE OR `the insurance of a minor is not modelled`

-- A refusal cannot be caught.

#EVAL NOT `the insurance of a minor is not modelled`
#EVAL CONSIDER covered FALSE TRUE
        WHEN TRUE  THEN "covered"
        WHEN FALSE THEN "not covered"

-- Testing a refusal.

#ASSERT REFUSED `the fee in` 1999
#ASSERT REFUSED `the fee in` 1999 BECAUSE "this schedule is not encoded for years before 2000"
#ASSERT REFUSED covered FALSE TRUE
    BECAUSE "the insurance of a minor is not modelled"
#ASSERT `the fee in` 2024 EQUALS 100
#ASSERT NOT (FALSE AND `the insurance of a minor is not modelled`)
</code></pre>
<h2 id="examples">Examples</h2>
<p>Give each reason a definition of its own, named for what is not encoded, and use the name where the rule needs it:</p>
<pre><code class="language-l4">GIVETH A NUMBER
`fees before 2000 are not encoded` MEANS
    REFUSE "this schedule is not encoded for years before 2000"

GIVEN year IS A NUMBER
GIVETH A NUMBER
`the fee in` year MEANS
    IF year >= 2000
    THEN 100
    ELSE `fees before 2000 are not encoded`

#EVAL `the fee in` 2024
#EVAL `the fee in` 1999
</code></pre>
<p>The first <code>#EVAL</code> gives <code>100</code>, and the second prints:</p>
<pre><code class="language-text">The model refuses to answer:
  this schedule is not encoded for years before 2000
</code></pre>
<p>A rule that answers yes or no refuses the same way:</p>
<pre><code class="language-l4">GIVETH A BOOLEAN
`the insurance of a minor is not modelled` MEANS
    REFUSE "the insurance of a minor is not modelled"

GIVEN adult   IS A BOOLEAN
      insured IS A BOOLEAN
GIVETH A BOOLEAN
DECIDE covered IS
    IF adult
    THEN insured
    ELSE `the insurance of a minor is not modelled`
</code></pre>
<p><code>covered TRUE TRUE</code> is <code>TRUE</code>, and <code>covered FALSE TRUE</code> refuses, with the reason "the insurance of a minor is not modelled".</p>
<p>To use one refusal in rules of different types, declare it for any type, with <code>GIVEN a IS A TYPE</code> and <code>GIVETH AN a</code>:</p>
<pre><code class="language-l4">GIVEN a IS A TYPE
GIVETH AN a
`not written yet` MEANS
    REFUSE "this rule has not been written yet"

GIVETH A NUMBER
`the deposit` MEANS 1 PLUS `not written yet`

GIVETH A BOOLEAN
`the deposit is refundable` MEANS `not written yet`
</code></pre>
<p>Both rules refuse, with the reason "this rule has not been written yet".</p>
<h2 id="which-refusals-are-reached">Which refusals are reached</h2>
<p><code>AND</code>, <code>OR</code> and <code>IF</code> read from left to right, and stop as soon as the answer is known, so a <code>REFUSE</code> they do not reach does not refuse:</p>
<pre><code class="language-l4">#EVAL FALSE AND `the insurance of a minor is not modelled`
#EVAL `the insurance of a minor is not modelled` AND FALSE
#EVAL TRUE OR `the insurance of a minor is not modelled`
</code></pre>
<p>The first gives <code>FALSE</code> and the third <code>TRUE</code>.
The second refuses, because it reaches the refusal before the <code>FALSE</code>.
So write first what settles the cases a rule encodes, and the refusal where only the other cases reach it, as <code>covered</code> does with its <code>IF</code>.</p>
<h2 id="a-refusal-cannot-be-caught">A refusal cannot be caught</h2>
<p>Once a rule reaches a <code>REFUSE</code>, everything that needs its value refuses too, with the same reason.
No construct turns a refusal back into a value: <code>NOT</code> of a refusal refuses, and so does a <code>CONSIDER</code> or an <code>IF</code> on one.</p>
<pre><code class="language-l4">#EVAL NOT `the insurance of a minor is not modelled`
#EVAL CONSIDER covered FALSE TRUE
        WHEN TRUE  THEN "covered"
        WHEN FALSE THEN "not covered"
</code></pre>
<p>Both refuse, with the reason "the insurance of a minor is not modelled".
A rule that uses a rule that refuses gives the same refusal to whatever uses it in turn.</p>
<h2 id="testing-a-refusal-assert-refused">Testing a refusal: <code>#ASSERT REFUSED</code></h2>
<p><code>#ASSERT REFUSED expression</code> holds when the expression refuses.
<code>#ASSERT REFUSED expression BECAUSE "reason"</code> holds when it refuses with exactly that reason.</p>
<pre><code class="language-l4">#ASSERT REFUSED `the fee in` 1999
#ASSERT REFUSED `the fee in` 1999 BECAUSE "this schedule is not encoded for years before 2000"
#ASSERT REFUSED covered FALSE TRUE
    BECAUSE "the insurance of a minor is not modelled"
</code></pre>
<p>The reason after <code>BECAUSE</code> is a string literal.
<code>BECAUSE</code> goes on the line of the <code>#ASSERT</code>, or at the start of a line of its own indented further than the <code>#ASSERT</code>.</p>
<p>An <code>#ASSERT REFUSED</code> reports one of these:</p>
<ul>
<li><code>assertion satisfied</code>, when the expression refuses, with the reason after <code>BECAUSE</code> if there is one;</li>
<li><code>assertion failed: expected a refusal, but the expression produced a value</code>, when it gives a value;</li>
<li><code>assertion failed: expected the refusal "…", got "…"</code>, naming both reasons, when it refuses with another reason;</li>
<li><code>assertion could not be evaluated:</code> and the cause, when its evaluation stops with an error, such as a division by zero or a term that is only <code>ASSUME</code>d;</li>
<li><code>assertion could not be evaluated:</code> and <code>The value goes deeper than a directive reads, so whether it refuses below that depth is not known.</code>, when it gives a value deeper than a directive reads, such as a list of more than 200 items.</li>
</ul>
<p>In <code>l4 run --json</code>, an <code>#ASSERT REFUSED</code> is a result whose <code>"kind"</code> is <code>"assertion"</code>, with <code>"value": true</code> when it holds, and <code>"value": false</code> and the message under <code>"error"</code> when it fails.</p>
<p>A plain <code>#ASSERT</code> of an expression that refuses reports <code>assertion refused:</code> and the reason, which is neither satisfied nor failed; see <a href="/l4/reference/syntax#what-assert-reports">What <code>#ASSERT</code> reports</a>.</p>

<p>The service answers a refusal with <code>200</code>, as it answers an answer, because declining is how the rules answer that case; a <code>422</code> is only an evaluation that stops with an error.
The body is tagged <code>Refused</code>, and its <code>contents</code> is the refusal, marked by <code>"kind": "refused"</code>:</p>
<pre><code class="language-json">{
  "contents": {
    "kind": "refused",
    "reason": "this schedule is not encoded for years before 2000"
  },
  "tag": "Refused"
}
</code></pre>
<p>An MCP tool call answers a refusal without <code>isError</code>, as it answers an answer, with that body as its text, so an agent relays the refusal instead of treating the tool as broken.
Tell a refusal by its <code>tag</code> or its <code>kind</code>: an answer's <code>contents</code> has a <code>result</code>.</p>
<h2 id="the-query-plan">The query plan</h2>
<p>A query plan names the inputs still needed to settle a rule's answer.
A rule that may refuse has no query plan, whatever it answers and whatever inputs are already known: the planner declines it, and names each reason the rule may refuse with.
A rule may refuse when a <code>REFUSE</code> is written in it, or in a rule it uses, directly or through others, in its own file or in one it imports, whether or not the inputs given reach that <code>REFUSE</code>.
The service answers such a rule with <code>400</code>, <code>"kind": "declined"</code>, the <code>rule</code>, its <code>reasons</code> and the sentence in the table above; <a href="/l4/reference/functions/DECIDE#the-decision-graph-and-the-query-plan">The decision graph and the query plan</a> says what else a plan can be declined for.</p>
<h2 id="in-a-rendered-document">In a rendered document</h2>
<p><code>l4 render</code> writes a <code>REFUSE</code> as "the model refuses to answer:" and the reason in quotes, wherever it sits.
Under <code>AND</code>, it is listed among the conditions that must all be true:</p>
<pre><code class="language-l4">GIVEN adult IS A BOOLEAN
GIVETH A BOOLEAN
DECIDE `may travel` IF
    adult AND REFUSE "travel is not modelled"
</code></pre>
<p>is rendered by <code>l4 render --format text</code> as</p>
<pre><code class="language-text">1. May travel if:
    (a) adult; and
    (b) the model refuses to answer: “travel is not modelled”.
</code></pre>
<p>Read such a line as the point at which the rule stops without an answer: the rule reaches it only when what comes before it has not settled the answer, here for an adult.
A refusal with a name of its own is written by its name, as <code>covered</code> reads "Otherwise: the insurance of a minor is not modelled".</p>
<h2 id="limits">Limits</h2>
<ul>
<li>The reason is the string literal beside <code>REFUSE</code>: <code>REFUSE 42</code> is a type error, and <code>REFUSE ("a" APPEND "b")</code> is a parse error.
In <code>REFUSE "a" APPEND "b"</code>, <code>REFUSE</code> takes <code>"a"</code> alone, so the rule refuses with the reason "a".</li>
<li>A directive prints the reason exactly as written, spaces included, and <code>REFUSE ""</code> refuses with an empty reason.</li>
<li><code>REFUSE</code> and <code>REFUSED</code> are keywords everywhere, though <code>REFUSED</code> is used only in <code>#ASSERT REFUSED</code>, so a name spelled either way is written in backticks: <code>DECLARE Status IS ONE OF Approved, REFUSED</code> is a parse error ("unexpected REFUSED"), and <code>DECLARE Status IS ONE OF Approved, `REFUSED`</code> checks.</li>
<li>An operator with more than one meaning must be able to tell the type of a refusal it is given.
Under <code>IMPORT daydate</code>, <code>PLUS</code> adds numbers and dates, so L4 must be able to tell whether a refusal added to a number stands for a number or for a date.
A <code>GIVETH A NUMBER</code> on a rule whose answer is the sum, or on the named refusal, tells it, so <code>`the deposit`</code> above checks under <code>IMPORT daydate</code>.
So does using the sum where only a number fits, as in <code>(1 PLUS REFUSE "…") TIMES 2</code>, or passing it to a function whose input is a number.
Brackets around the <code>REFUSE</code> do not tell it, and neither does declaring the refusal for any type.
Where nothing tells it, as in a rule <code>x MEANS 1 PLUS REFUSE "…"</code> with no <code>GIVETH</code>, or in <code>(1 PLUS REFUSE "…") EQUALS (1 PLUS REFUSE "…")</code> even in a rule with <code>GIVETH A NUMBER</code>, L4 reports "There are multiple definitions for the identifier".</li>
<li>The WASM backend (<code>jl4-mlir</code>) marks a function that may refuse, through its own <code>REFUSE</code> or one in a definition it calls, <code>"supported": false</code>, with the reason "REFUSE is not supported by the WASM backend".
Evaluate such a function with jl4-service, which reports its refusal as the table above says.</li>
</ul>
